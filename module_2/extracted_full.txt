1. Module Overview
Module 2 takes you into C — the language that sits closest to the hardware. Every RISC-V
simulator, every EDA tool backend, every firmware stack, and every embedded system is
written in C (or its close relatives). Understanding C is not about learning another programming
language; it is about understanding how a computer actually works at the machine level.
This module focuses on the aspects of C that matter most for hardware engineers: memory
layout, pointers, bitwise operations, structs that map to hardware registers, and low-level
patterns you will encounter when writing testbenches, firmware, and architecture simulators. We
deliberately skip topics like GUI programming or web development — everything here connects
to your future work with RISC-V.

Why C for Hardware Engineers?
When you write a RISC-V compliance test, the reference model is in C. When you write firmware for
an FPGA prototype, it is in C. When you read the RISC-V Spike simulator source code, it is C/C++.
When you interface with Verilator through DPI, you write C. C is not just a language — it is the bridge
between your RTL design and the real world.

Hardware Connection
Throughout this module, look for these purple boxes. They connect each C concept to a specific
hardware engineering application, showing you exactly why you need to know this.

Control Flow
Goal: Understand how C code becomes machine code, master fixed-width types, and perform
bitwise operations essential for hardware work.

4.1 The C Compilation Pipeline
Unlike interpreted languages (Python), C code goes through 4 distinct stages before it runs.
Understanding this pipeline demystifies many errors you will encounter:
1.​ Preprocessing (cpp): Expands #include, #define, #ifdef. Output: still C code, but
expanded.
2.​ Compilation (cc1): Translates C to assembly (.s file). This is where syntax and type
errors appear.
3.​ Assembly (as): Translates assembly to machine code object file (.o). Platform-specific
binary.
4.​ Linking (ld): Combines object files + libraries into a final executable. Resolves function
calls across files.
# See each stage explicitly:
gcc -E main.c -o main.i

# Step 1: Preprocessor output

gcc -S main.c -o main.s

# Step 2: Assembly output

gcc -c main.c -o main.o

# Step 3: Object file

gcc main.o -o main

# Step 4: Link into executable

# Or all at once (what you normally do):
gcc -Wall -Wextra -std=c11 -g -o main main.c
# Flag meanings:
# -Wall

Enable most warnings

# -Wextra

Enable extra warnings

# -std=c11

Use C11 standard

# -g

Include debug info (for GDB)

# -O0

No optimization (default, best for debugging)

# -O2

Optimize for speed (production builds)

Common Bit Manipulation Patterns
// Extract bits [high:low] from value
#define EXTRACT_BITS(val, high, low) \
(((val) >> (low)) & ((1U << ((high)-(low)+1)) - 1))
// Set bit N
#define SET_BIT(val, n)

((val) | (1U << (n)))

// Clear bit N
#define CLEAR_BIT(val, n)

((val) & ~(1U << (n)))

// Toggle bit N
#define TOGGLE_BIT(val, n) ((val) ^ (1U << (n)))

// Check if bit N is set
#define IS_BIT_SET(val, n) (((val) >> (n)) & 1U)
// Sign-extend a value from bit_width to 32 bits
int32_t sign_extend(uint32_t val, int bit_width) {
uint32_t sign_bit = 1U << (bit_width - 1);
return (int32_t)((val ^ sign_bit) - sign_bit);
}

Hardware Connection: Instruction Decoding
The bit extraction code above is EXACTLY what your RISC-V processor does in hardware. In Verilog,
you write assign opcode = instruction[6:0]. In C, you write (instruction & 0x7F). Same operation,
different syntax. Mastering this in C prepares you to think like the hardware.

4.4 Control Flow
Quick revision of control flow since you know this from prior courses, with emphasis on
hardware-relevant patterns:
// switch-case: PERFECT for opcode decoding
switch (opcode) {
case 0x33: // R-type
execute_r_type(instruction);
break;
case 0x13: // I-type (immediate)
execute_i_type(instruction);
break;
case 0x23: // S-type (store)
execute_s_type(instruction);
break;
case 0x63: // B-type (branch)
execute_b_type(instruction);
break;
default:
fprintf(stderr, "Unknown opcode: 0x%02X\n", opcode);
break;
}
// Ternary operator: useful for mux-like selections
uint32_t result = (opcode == 0x33) ? alu_result : immediate;

5.2 Pointers — The Heart of C
A pointer is a variable that holds a memory address. Every pointer has two attributes: the
address it stores, and the type of data it points to (which determines how many bytes to
read/write when dereferenced).

Pointer Arithmetic
When you add 1 to a pointer, it advances by sizeof(*ptr) bytes, not 1 byte. This is why pointer
type matters:
uint32_t memory[8] = {0};

// Simulated 32-byte memory

uint32_t *word_ptr = memory;
// word_ptr + 1

moves forward 4 bytes (sizeof(uint32_t))

// word_ptr + 2

moves forward 8 bytes

*(word_ptr + 3) = 0xFF;

// Same as memory[3] = 0xFF

// Byte-level access to the same memory:
uint8_t *byte_ptr = (uint8_t *)memory;
// byte_ptr + 1

moves forward 1 byte

*(byte_ptr + 12) = 0xAB;

// Writes to byte 12 = word 3, byte 0

5.3 Arrays
// Arrays are contiguous blocks of memory
uint32_t registers[32] = {0};

// 32 RISC-V registers, initialized to 0

registers[0] = 0;

// x0 is always 0 in RISC-V

registers[2] = 0x7FFFFFF0;

// sp (stack pointer)

// Array name IS a pointer to the first element
uint32_t *reg_ptr = registers;

// No & needed!

// registers[i] is equivalent to *(registers + i)
// 2D array: memory as rows x columns
uint8_t cache[4][64];

// 4 cache lines, 64 bytes each

cache[0][0] = 0xFF;

// First byte of first line

// Array size calculation
size_t num_regs = sizeof(registers) / sizeof(registers[0]);

// 32

Arrays Have No Bounds Checking!
C does NOT check array bounds. Writing registers[32] will silently corrupt adjacent memory. This is
the source of countless bugs and security vulnerabilities. Always validate indices.

5.5 Functions with Pointers (Pass-by-Reference)
// C is ALWAYS pass-by-value. To modify the caller's data, pass a
pointer.
// Swap two register values
void swap_registers(uint32_t *a, uint32_t *b) {
uint32_t temp = *a;
*a = *b;
*b = temp;
}
// Passing an array (decays to pointer automatically)
void clear_registers(uint32_t regs[], size_t count) {
for (size_t i = 0; i < count; i++) {
regs[i] = 0;
}
}
// const pointer: promise not to modify data through this pointer
void print_memory(const uint8_t *mem, size_t size) {
for (size_t i = 0; i < size; i++) {
printf("%02X ", mem[i]);
}
}

6.1 Structs — Grouping Related Data
Structs let you group related variables into a single type — perfect for modeling hardware
structures:
// Model a RISC-V decoded instruction
typedef struct {

uint32_t rd;

uint32_t rs2;

decoded_instr_t instr;

instr.rd = 4;
instr.rs1 = 5;
instr.rs2 = 10;
// Pointer to struct (very common pattern)

Hardware Connection: Register Definition
When you write device drivers for RISC-V peripherals, you define a struct that maps directly to the
peripheral’s register layout. The struct’s field offsets must match the hardware register addresses.
Padding awareness is critical — a wrong offset means you read the wrong register.

Bit-field Portability Warning
The layout of bit-fields (order, padding) is implementation-defined and varies between compilers and
endianness. For portable code, use explicit shift-and-mask operations. Bit-field structs are great for
readability and debugging but should not be relied upon for cross-platform correctness.

The Four Deadly Memory Sins
5.​ Memory Leak: malloc without matching free. Memory grows until crash.
6.​ Dangling Pointer: using a pointer after free. Random data or crash.
7.​ Double Free: calling free() twice on same pointer. Heap corruption.
8.​ Buffer Overflow: writing past the allocated boundary. Corrupts other data.
